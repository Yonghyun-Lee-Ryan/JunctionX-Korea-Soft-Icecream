# 심사 기준

> [!error] 이 문서가 하네스에서 가장 중요하다
> 기획에는 컴파일러가 없지만 해커톤에는 **심사 기준**이 있다. 이게 유일한 객관적 판정자다.
> **공식 기준이 나오면 요약하지 말고 원문 그대로 붙여넣을 것.** 요약하는 순간 판정자가 무뎌진다.

> [!important] 🔴 기준을 읽는 관점 — **문제의 소유자는 Challenge Partner다** (2026-08-21)
> 어떤 항목이 나오든, 우리가 푸는 것은 **파트너가 자기 사업에서 돈·시간·리스크를 쓰고 있는 과제**다. 사용자·유저플로우·화면은 그대로 만든다(미션 1이 유저플로우를 요구하고 Expo 3시간은 화면으로 버틴다). 바뀌는 건 **「누구의 문제를 푸는가」의 답**이다.
> **충돌하면 이 순서로 이긴다** — ①트랙 적합성 → ②파트너의 사업적 동기 → ③파트너가 「그건 아니다」라고 말한 것 → ④파트너 담당자 발화 → ⑤개인 페르소나·개인 pain point. **⑤는 지우는 게 아니라 마지막이다.**

### Upstage 트랙 — Evaluation Criteria (원문 · 총 100점)

```
Criteria                                  Evaluation Factor

Upstage Technology Implementation (30)    How deeply the team leveraged Upstage Studio and its APIs
                                          — agent composition, external integrations, and the difficulty and
                                          accuracy of the implementation.

Service Completeness (20)                 Does the demo run reliably end to end?
                                          Are the screens, flows, and UX polished enough to be called a real
                                          service?

Idea Creativity (25)                      Is the problem discovery fresh?
                                          Does the solution stand apart from existing services?

Product Planning (25)                     Concrete target users and problem definition, well-prioritized scope
                                          within the 3-day constraint, and a screen & data-flow design solid enough
                                          to become a real service.
```

| **기술적 도전** | 어려운 걸 했는가 | API 호출 몇 개 조합 |
| **독창성** | 이미 있는 것과 무엇이 다른가 | 기존 서비스 재현 |
| **트랙 적합성** | 챌린지 파트너가 낸 과제에 답했는가 | **과제를 무시하고 하고 싶은 걸 함** |
| **발표** | 3분 안에 전달되는가 | 배경 설명에 2분 씀 |

마지막에서 두 번째 줄이 실무에서 가장 자주 깨지는 지점이다. 트랙 파트너는 **자기 과제의 답**을 보러 왔다.
