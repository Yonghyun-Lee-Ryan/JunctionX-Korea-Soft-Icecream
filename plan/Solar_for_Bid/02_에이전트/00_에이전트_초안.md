# Studio 에이전트 초안

> [!summary]
> `solar_for_bid_agent.json` — **Upstage 자체 제작 `Federal RFPs`의 공개 설정과 같은 구조**로 쓴 Solar for Bid 에이전트 정의. 52KB.
> Studio는 JSON 임포트를 제공하지 않으므로 **이 파일은 원본이고, UI에 손으로 옮겨 넣는다.** 어느 칸에 무엇을 넣는지는 아래 2절.
> 생성 스크립트는 `build_agent.py` — 스키마를 고칠 때 md를 고치지 말고 **스크립트를 고쳐서 다시 뽑는다.**

## 1. 무엇이 들어 있나

```
Parse (ocrMode=force · coordinates=true · mergeMultipageTables=TRUE · location=true)
 └ classify-doc-kind ─ 9갈래 · Split ON
     │  ntce_notice · rfp_main · sow_task · req_spec · eval_sheet
     │  contract_terms · form_annex · 🆕 our_proposal · others
     │
     ├━ Must 5 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
     │  cross_check_notice_vs_rfp ← ntce_notice + rfp_main       🔴 공고서가 이긴다
     │    └ judge_eligibility     ← cross_check + rfp_main + 회사프로필
     │  compliance_matrix         ← req_spec + rfp_main
     │    └ build_wbs             ← compliance_matrix + sow_task
     │       └ critical_path      ← build_wbs + ntce_notice
     │
     └━ Should 5 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
        analyze_scoring            ← eval_sheet + rfp_main       배점 해부·커트라인 역산
        triage_contract_risk       ← contract_terms              낙찰 후 지는 의무
        build_submission_checklist ← form_annex + rfp_main       ※ 인정범위 규칙
        draft_questions            ← cross_check + matrix + judge  묻지 않을 것 포함
        🆕 check_proposal_coverage ← our_proposal + matrix       🔴 우리 제안서를 되태운다
```

> [!success] 🟢 이번 판에서 고친 것 — 검사로 잡았다
> **고아 스키마 5개 → 0개.** 직전 판은 Extract 7개 중 5개를 뽑기만 하고 아무 Instruct도 읽지 않았다. 그중 둘은 버그였다:
> - 🔴 `judge_eligibility`가 **참가자격(`ie_rfp_main`)을 못 봤다** — 자격 판정의 근거가 파이프라인에 안 들어왔다
> - 🔴 `build_wbs`가 **과업내용서(`ie_sow_task`)를 못 봤다** — WBS의 원재료가 끊겨 있었다
>
> 원인은 하나다. 「Instruct는 소스 하나만 받는다」(Federal RFPs 관찰)에 맞추다가 필요한 입력을 잘랐다.
> **`_inputs`가 실제로 필요한 입력이고 `connectionMapping`은 관찰된 단일 소스 형태다.** 04:00에 캔버스가 다중 입력을 허용하면 `_inputs`대로 잇고, 아니면 우리 Node 층이 합쳐 Solar Pro 4로 보낸다.
> 🟢 **Must 5는 Should에 의존하지 않는다** (폐쇄성 검사 통과) — 시간이 없으면 Must만 만들어도 데모가 돈다.

## 2. Studio UI 어느 칸에 넣나

| JSON 블록 | Studio UI 위치 |
|---|---|
| `documentParseConfiguration` | Parse 노드 우측 패널 |
| `documentClassifyConfiguration.schema.json_schema.schema.oneOf[]` | Classify 노드 **스키마 표** — 행마다 `const`를 레이블 칸에, `description`을 설명 칸에 |
| Split | Classify 패널 **「Split 활성화」 토글 ON** |
| `informationExtractConfiguration.schemas[]` | Extract 노드 7개 — 노드 이름을 `json_schema.name`으로, 필드는 스키마 편집기에 |
| `categorySchemaMapping` | Classify 갈래와 Extract 노드를 캔버스에서 잇는 선 |
| `instructConfiguration.nodes[]` | Instruct 노드 10개 — **Must 5부터** — `name`을 노드 이름, `prompt`를 프롬프트 칸에 |
| `connectionMapping` | Instruct 노드가 **무엇을 읽는지** 잇는 선 |

🔴 **노드 이름을 반드시 짓는다.** 안 지으면 `instruct-6` 같은 기본 이름이 남는다 — Upstage 자체 데모 p23이 실제로 그렇다.

## 3. 🔴 Federal RFPs와 대조 — 정직한 표

| | Federal RFPs | Solar for Bid |
|---|---:|---:|
| Classify 갈래 | 4 | **9** |
| Extract 스키마 | 4 | **8** |
| Extract leaf 필드 | **210** | 156 |
| Instruct 노드 | 2 | **10** (Must 5 / Should 5) |
| Instruct 체인 깊이 | 2단 | **3단** (체인 둘) |
| `ocrMode` | `force` | `force` (같음 — 그들에게 배웠다) |
| `mergeMultipageTables` | `false` | **`true`** |
| Extract `location`(좌표) | `false` | **`true`** |
| `language` | `en` | `ko` |

> [!error] 🔴 양으로 자랑하지 않는다 — 두 번째 교훈
> 노드 개수 때 이미 한 번 걸렸다(실물 캔버스 p23이 16노드인데 우리 14노드를 「최대 4 대비 3.5배」라고 썼다). **필드 수도 마찬가지다 — 우리 156, 그들 210으로 우리가 적다.**
> 부스에서 말할 것은 **개수가 아니라 설정 넷**이다:
> ① **Split ON** — 공개 에이전트 29개 중 사용 0, Federal RFPs도 OFF
> ② **`mergeMultipageTables: true`** — 한국 요구사항 표는 수십 쪽에 걸쳐 이어진다
> ③ **Extract `location: true`** — 값마다 좌표를 받는다. 「페이지 인용」이 여기서 나온다. 그들은 `false`다
> ④ **문서군 두 개를 맞댄다** — 공고 문서 ↔ 회사 프로필. 29개도 Federal RFPs도 전부 한 종류 문서만 본다

## 4. 🔴 04:00 프리플라이트에서 확인할 것 — 설계 전제 넷

| # | 전제 | 깨지면 |
|---|---|---|
| 1 | **Instruct 노드가 소스를 하나만 받는다** (Federal RFPs `connectionMapping` 관찰) | 여러 문서를 합쳐야 하는 판정은 **우리 Node 층 + Solar Pro 4 API**로 내린다. Studio 체인은 단일 소스만 |
| 2 | **Instruct가 Instruct를 받는다** (3단 체인) | 2단으로 축소한다 — 2단은 Federal RFPs가 실제로 도는 것을 확인했다 |
| 3 | **Split이 한 파일 안의 섹션을 가른다** | 파일 단위 분류로 후퇴. 🟢 데모 공고는 첨부가 이미 5개라 **최소 4갈래는 확보된다** |
| 4 | `req_spec` 세로 라벨 표에서 **행이 몇 % 살아남는가**, **`※`가 보존되는가** | 조견표를 빼고 WBS·임계경로로 좁힌다 |

## 4-1. 🔴 `cross_check_notice_vs_rfp` — 왜 이 노드가 생겼나

조달 실무의 기본 규칙 하나가 리서치에서 확인됐다 — **공고서와 제안요청서(규격서)의 내용이 다르면 공고서가 우선한다.** 그리고 실무자가 가장 흔히 하는 사고가 *"RFP만 읽고 공고문을 안 읽는 것"*이다. 사람은 200쪽을 두 번 읽지 못한다.

**우리는 두 문서를 같은 파이프라인으로 읽으므로 불일치가 기계적으로 드러난다.** 비교 대상 — 사업명 · 사업기간 · 추정가격/배정예산 · 계약방법 · 마감일시 · 제출방법 · 부수 · 분량상한 · 참가자격 · 배점 비율 · 설명회 실시 여부.

판정 어휘는 Solar Pro 4 공식 3분류 그대로 — `grounded` / `not-in-document` / `mismatch`. 값이 다르면 **공고서 값을 정답으로 표시**하고 두 쪽 번호를 다 붙인다. 🔴 표기 차이(`4억` vs `400,000,000원`)는 mismatch가 아니다.

## 4-2. 🆕 `check_proposal_coverage` — 세 번째 문서군

다른 아홉 갈래는 **발주기관이 낸 문서**를 읽는다. 이 노드만 입력이 **우리가 쓴 제안서**다.

- 요구사항 조견표의 각 ID가 제안서 본문에서 다뤄졌는지 대조 → **미대응 N건**
- 🔴 **금지 표현 전수 검색** — RFP가 열거한 「가능하다」·「고려할 수 있다」 류가 남아 있으면 그 문장과 쪽을 그대로. 평가에서 **불가능한 것으로 간주**되는 표현이다
- 분량 상한·부수·일련번호·지정 양식 준수
- 🔴 **문장을 고쳐 주지 않는다.** 걸린 자리만 짚는다 — 고치는 것은 사람이다

이 노드가 있어야 「미대응 요구사항 0건」이 화면에 뜬다. **그게 이 제품의 끝 문장이다.**

## 5. 프롬프트 규율 — 열 노드 공통

전부 p21 패턴(`return this output verbatim with the bracketed sections filled in`)을 쓰고, 아래 규율을 각 프롬프트에 박았다.

- **판정 어휘 고정** — 자격은 `충족 / 미충족 / [확인필요]` 셋뿐
- **근거 강제** — 모든 판정에 회사 프로필 항목명 + 공고 쪽 번호
- **지어내지 않기** — 프로필에 없는 실적·자격을 만들지 않는다. 문서에 없는 기간·날짜를 만들지 않는다
- **법령 해석 금지** — 조문 이름만 그대로 옮긴다
- **사람 칸 비우기** — 조견표의 「수용 여부」는 비운다
- **검산 블록 필수** — `compliance_matrix`는 분류별 총괄표 개수 ↔ 추출 개수를 대조하고, `build_wbs`는 요구사항 ID 미연결 작업을 나열한다
