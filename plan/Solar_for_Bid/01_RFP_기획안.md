## 1. Executive Summary

한국 공공·금융 조달의 제안 담당자는 공고 하나를 받으면 **HWP 여섯 개, 200쪽**을 손으로 뜯는다. 마감까지 달력으로 9일이어도 공휴일을 빼면 **실질 5영업일**이고, 그 5일 동안 하는 일은 다섯이다 — 참가자격 판정 · 요구사항 조견표 작성 · 일정과 투입인력 설계 · 원가 산정 · 배점 역산. **첫 번째에서 틀리면 나머지 나흘이 통째로 무의미하다.**

**Solar for Bid는 나라장터 공고번호 하나를 받아 조달 절차를 한 줄로 잇는다.** 첨부 HWP를 자동으로 끌어오고(S1), Upstage Studio가 **읽고·가르고·뽑고**(S2), **참가자격을 대조해 낼지 말지를 페이지 인용과 함께 닫고**(S3), 요구사항 조견표(S4) · WBS와 임계경로와 원가(S5) · 질의서 초안(S6) · 제출 체크리스트(S7)를 만든다.

🔴 **S8 투찰은 하지 않는다.** 공동인증서와 지문인식보안토큰으로 잠긴 구간이다. **우리의 end는 「제출할 수 있는 상태」**이고, 그 벽을 숨기지 않고 화면에 그린다 — 숨기면 현업 심사 첫 질문에 무너진다.

**Upstage에게 이 제품은** ① 자사 `Federal RFPs` 에이전트가 멈춘 세 자리 — **한국·회사·끝** — 를 채우는 것이고 ② 고객의 **52.5%가 금융권**이며 회사가 **2025-12 조달청 디지털서비스몰 첫 공급사**인, 이미 발을 들인 도메인이며 ③ 라이브러리 29개가 전부 「심사·처리하는 쪽」인 자리에서 **「서류를 내는 쪽」**의 두 번째 사례다.

**48시간이 증명하는 칸은 하나다** — 「공고 한 건이 들어와서 S1→S5가 끊기지 않고 이어지고, 끝에 제출물 파일이 나온다」. S0·S6·S7은 경로만 그린다.

## 2. 기획 의도

### 2-1. 왜 이 문제인가 — 「이해」는 팔리고 있고, 「제출물」은 아무도 안 만든다

트랙 과제문은 *"goes beyond **'understanding'** documents to actually **'getting the work done.'**"* 라고 못 박았다.

조달에서 **understanding은 이미 상품이다.** 클라이원트(2023 창업·20억 투자)가 300+ 채널 공고 수집 → RFP 본문 자동 분석(150쪽 이상) → 요구사항 체크리스트 → Go/No-Go 근거 데이터를 3년째 판다. 올거나이즈는 RFP를 과거 제안 이력과 대조해 전략 리포트를 낸다.

**아무도 안 하는 것은 그 다음이다.** 확인된 국내외 16개 서비스 중:

| | 하는 곳 |
| --- | --- |
| 공고 알림·추천 | 다수 (나라장터·지투비플러스는 **무료**) |
| 투찰가 예측 | 6곳 (ML 학습, 수백만 건 데이터) |
| RFP 본문 분석·요약 | 3곳 |
| 요구사항 표 | 2~3곳 |
| 🔴 **WBS** | **0곳** |
| 🔴 **Critical Path** | **0곳** |
| 🔴 **문서 근거를 붙인 자격 미충족 선언** | **0곳** |

→ **기획 의도 한 줄**: *"조달 문서에서 「이해」는 이미 팔린다. 우리는 그 문서를 **제출할 수 있는 산출물**로 바꾸는 첫 자리를 만든다."*

**근거 — 회사가 이미 만들었고, 멈췄다**

### 2-3. 왜 지금인가 — 실호출로 열린 문 둘

이 기획은 두 달 전에는 못 세웠다. **오늘 02:20~02:30에 확인한 것 둘이 전제다.**

| 열린 것 | 값 |
| --- | --- |
| **나라장터 첨부가 인증 없이 받아진다** | `GET .../UntyAtchFile/downloadFile.do?bidPbancNo=&bidPbancOrd=&fileType=&fileSeq=` → HTTP 200, 쿠키·로그인·키 전부 불필요 |
| **Parse가 그 HWP를 그대로 받는다** | `file` 판정 `Hangul (Korean) Word Processor File 5.x`. **변환 단계가 통째로 없다** |

→ 이 둘이 만나서 **「공고번호 한 줄 → 문서 묶음 → 판정·산출물」**이 34시간에 가능해졌다.
🔴 그리고 **공공데이터포털 API 키가 선행조건이 아니다** — 첨부는 키 없이 받아지고, 메타는 공고문 HWP에서 뽑으면 된다. **키 승인 대기가 데모를 막지 않는다.**

### 3-2. 타깃 — 한 사람, 그리고 당사자성

**타깃** — 중소 IT 컨설팅·SI 기업(임직원 50~100명)의 **제안 담당자**. 연 10~20건 검토, 그중 3~5건 응찰.

**페르소나** — 제안팀 과장. 금요일 오후 공고 하나를 받는다. 첨부 HWP 다섯, 합쳐 200쪽. 마감은 다음 주 목요일 14:00 인편. 달력으로 6일인데 공휴일이 껴서 **4영업일**. 월요일 아침까지 「낼까 말까」를 답해야 하는데, 그 답의 근거는 200쪽 안 어딘가에 있다.

> [!warning] 🔴 「problems students genuinely relate to」에 대해 — 정직하게
> 트랙 원문은 *"**Any domain is welcome** — problems students genuinely relate to are especially encouraged."* 앞 문장이 요건이고 뒷 문장은 **가점 신호**다. **우리는 뒷 문장을 못 채운다.** 인정하고 다른 칸으로 갚는다:

> - **화면 첫 단어에서 「공공 입찰」을 지운다.** *"정부가 낸 공고문 한 장"* 으로 시작한다 — 학생도 아는 물건이다(장학금 공고와 같은 HWP 서식)
> - ⚠️ **외부 당사자 인터뷰는 0건이다.** 8/22 낮 창구에서 채우거나, 못 채우면 **발표에서 먼저 밝힌다** → 13절 R3

## 4. 서비스 정의

### 4-1. 핵심 가치 한 문장

> **"나라장터에 공고가 뜨면, 낼지 말지부터 낼 것을 다 갖추기까지가 한 줄로 이어진다."**

산출물 네 개(조견표·WBS·임계경로·원가)는 **제품의 정의가 아니라 특정 단계의 출력**이다. 제품은 **파이프라인**이다.

### 4-2. 🔴 E2E 파이프라인 — 공고 게시부터 제출 직전까지 8단계

조달은 원래 단계가 정해진 일이다. 우리는 그 단계를 새로 만들지 않고, **이미 존재하는 절차에 문서 에이전트를 한 줄로 꿴다.**

```
 ┌─ S0 발주 전 신호 ─────────── 발주계획 내역 API · 사전규격 공개
 │      (Should · v2)          「이 기관이 이걸 낼 것 같다」
 ▼
 ┌─ S1 수집 ────────────────── 공고번호 → 첨부 fileSeq 1..N 자동 수집
 │      🟢 Must               인증 불필요 · 422가 끝 · UA 필수
 ▼
 ┌─ S2 해부 ────────────────── Parse → Classify 7갈래(Split ON) → Extract ×7
 │      🟢 Must               문서 묶음이 7종으로 갈리고 값이 좌표와 함께 나온다
 ▼
 ┌─ S3 판정 ────────────────── Instruct: judge-eligibility
 │      🟢 Must ★심장          회사 프로필 ↔ 참가자격 대조 → Go / No-Go / 조건부
 │                            + 부정당제재·조달업체 등록 API로 교차 확인
 │      🚪 사람 게이트: 최종 참여 결정
 ▼
 ┌─ S4 요구 정리 ───────────── Instruct: build-compliance-matrix
 │      🟢 Must               요구사항 조견표 + ※ 단서 보존 + ID 검산 → 조견표.xlsx
 ▼
 ┌─ S5 계획 ────────────────── Instruct: build-wbs → build-critical-path
 │      🟢 Must               WBS · 제안준비/사업수행 두 임계경로 · 예상 원가
 ▼
 ┌─ S6 질의 ────────────────── Instruct: draft-questions
 │      🟡 Should             모호·상충 조항 → 질의서 초안 + 「묻지 않을 것」
 │      🚪 사람 게이트: 발송 (질의는 전 제안사에 공유된다)
 ▼
 ┌─ S7 제출 준비 ───────────── 제출 체크리스트 · 서류 부수 · 유효기간 · 금지표현 검사
 │      🟡 Should             → 체크리스트.xlsx
 │      🚪 사람 게이트
 ▼
 ┌─ S8 투찰 ────────────────── 🔴 **자동화하지 않는다**
        ⛔ Wont               공동인증서 + 지문인식보안토큰이 필요하다. 기계의 영역이 아니다
                              우리는 「무엇을 언제 어디에 내야 하는지」까지만 간다
```

🔴 **S8을 안 하는 것이 이 설계의 정직함이다.** 전자입찰 투찰은 인증서·생체 토큰으로 잠겨 있다 `[확인필요: 현행 토큰 정책]`. 「end to end」를 주장하면서 그 벽을 숨기면 현업 심사에서 첫 질문에 무너진다. **우리의 end는 「제출할 수 있는 상태」이고, 그 선을 화면에 그린다.**

```
   │      공고번호 → fileSeq 1..N → HWP/HWPX 묶음
   ▼
 [이해]  Parse → Classify(7갈래·Split ON) → Extract×7          ← Studio (p27 must power)
   │      읽기      문서 종류 가르기        갈래별 다른 스키마
   ▼
 [판정]  Instruct 4단 체인                                      ← Studio
   │      자격판정 → 조견표 → WBS → 임계경로
   │      Extract confidence low → 「확인 필요」로 사람에게
   ▼
 [산출]  파일 4종 생성 + 「미대응 요구사항 0건」                   ← 우리 (Node)

```

🔴 **즉사 경계** — Studio가 이미 하는 것(OCR·표 복원·분류·필드 추출·좌표 하이라이트·규정 대조 판정·문서 Q&A)은 **쓰고, 그 뒤를 만든다.** 우리 것은 **수집(앞)**과 **파일 생성(뒤)** 둘이다. 라이브러리 공개 에이전트 29개 중 `exportEnabled`를 쓴 것이 **0개**라는 것이 그 자리가 비어 있다는 증거다.

### 4-7. Federal RFPs가 멈춘 자리 — 우리 좌표

Upstage 자신의 RFP 에이전트를 공개 API로 재구성한 것:

```
Parse (document-parse-260128 · mode=auto · ocrMode=force · coordinates=true
       outputFormats=[html,text] · base64Encoding=[figure] · mergeMultipageTables=false)
 └─ Classify-1 ─ 4갈래: negotiated_rfp / simplified_rfq / task_order / idiq_base_vehicle
      └─ Extract ─ categorySchemaMapping으로 갈래별 스키마 4벌 (각 ~40필드)
           └─ Instruct: prep_kit    ─ compliance_matrix + submission_checklist + bid_readiness_flags
                └─ Instruct: risk_triage ─ 조항 위험 분류 + 상위 3~5건
```

| 없는 것 | 근거 | Solar for Bid |
| --- | --- | --- |
| **한국** | `language:"en"`. FAR·Section L/M·SF-1449·CLIN·NAICS 어휘. HWP 개념 없음 | 나라장터·협상에의한계약·요구사항조견표·기술90:가격10·인편접수 어휘. **HWP/HWPX 직접** |
| **회사** | Extract ~40필드가 **전부 공고 쪽**. 우리 회사가 충족하는지 대조하지 않는다 | 회사 프로필과 **기계 대조** → 미충족을 페이지 인용과 함께 선언 |
| **외부 연동** | **없다.** 사람이 파일을 올려야 시작한다 | **나라장터 자동 수집** |
| **끝** | `prep_kit`(분석)에서 멈춘다. WBS·임계경로·원가·파일 없음 | **파일 4종** |

> [!error] 🔴 여기서 **베낄 것**과 **자랑하면 안 되는 것**
> **베낀다**: `ocrMode:"force"`(회사 자신이 RFP에 OCR을 강제한다) · Classify 설명문 3단 작법(Distinguishing → KEY NEGATIVE → KEY DISTINCTION) · Extract 필드 정규화 규칙 · **Instruct가 Instruct를 받는 체이닝**
> 🔴 **자랑하지 않는다 — 노드 개수.** 공개 API 플래그는 노드 **종류**(최대 4종)를 세는 값이지 개수가 아니다. **실물 캔버스 p23이 16노드·7갈래**이고 **우리 14노드는 그보다 적다.** 개수로 말하면 그 자리에서 반증된다.

| (선택) 메타 | `https://apis.data.go.kr/1230000/**ad**/BidPublicInfoService/getBidPblancListInfoServcPPSSrch` → 403 코드 30(경로 정상, 키만 필요). 🔴 구 경로 `/1230000/BidPublicInfoService/`는 **코드 12로 폐기** |

🔴 **키가 없어도 v1은 완결된다.** 메타를 공고문 HWP에서 Extract로 뽑는다.

### 5-3. Studio 에이전트 그래프 — 7갈래 + others, **14노드**

```
Parse ─ mode=auto · ocrMode=force · coordinates=true · outputFormats=[html,text]
 │       base64Encoding=[figure] · 🔴 mergeMultipageTables=TRUE
 │       (Federal RFPs는 false. 한국 요구사항 표는 수십 쪽에 걸쳐 이어진다)
 └─ classify-doc-kind ─ Split 활성화 ON ─ 7갈래 + others
      ├─ ntce_notice    → ex-notice  ┐
      ├─ rfp_main       → ex-rfp     │
      ├─ sow_task       → ex-sow     │   Instruct-1  judge-eligibility  (자격 판정)
      ├─ req_spec       → ex-req     ├→        ↓
      ├─ eval_sheet     → ex-eval    │   Instruct-2  build-compliance-matrix
      ├─ form_annex     → ex-form    │        ↓
      ├─ contract_terms → ex-terms   ┘   Instruct-3  build-wbs
      └─ others         → 「분석 대상 아님」    ↓
                                        Instruct-4  build-critical-path
```

🔴 **Split ON이 Federal RFPs와 갈리는 지점이다.** 그들은 껐다(문서 1건 = 유형 1개). 한국 조달은 **한 건에 문서 여럿이 딸려 오고, 제안요청서 한 파일 안에 요구사항·배점표·서식이 함께 있다.**

### 5-4. Agents API 호출 흐름 — **폴링**

```
Flutter ──공고번호──▶ Node ──[0] fileSeq 1..N 수집 (키 불필요) ──▶ HWP 묶음
                     Node ──[1] 파일 업로드 ──────────────────▶ file_id
                     Node ──[2] Job 생성 (agent_id + config_id) ▶ job_id
                     Node ──[3] Job 조회 2~5s ─────────────────▶ status · 결과 · confidence
```

🔴 **webhook 없음 — 폴링 확정.** 처리는 *"보통 분 단위"*. **실패한 실행은 과금되지 않는다** → 재시도 단순화. Config 버전은 데모 전날 고정하고 그 뒤 캔버스를 건드리지 않는다.

### 5-5. 판정 어휘와 검산 — 우리가 쓰는 유일한 「규율」

| 층 | 규칙 |
| --- | --- |
| **판정 어휘** | 자격은 `충족 / 미충족 / [확인필요]` 셋뿐. 값은 `grounded / not-in-document / mismatch` |
| **근거 강제** | 모든 grounded 판정에 **페이지 번호**. Extract가 좌표를 주므로 원문 대조가 가능하다 |
| **지어내지 않기** | 회사 프로필에 없는 실적·자격을 만들지 않는다 → `[확인필요]`. 법령을 **해석하지 않는다**(조문 이름만 그대로 옮긴다) |
| **confidence 분기** | Extract `low` → 화면에 ⚠ + 사람 확인. `high`만 자동 진행 |
| 🔴 **검산 셋** | ① 조견표 행 수 = 목록표 ID 수(**ID 대조**까지) ② **배점 소계 = 항목합**(총합만 보면 못 잡는다 — 실물에서 (10) vs 11, (10) vs 9가 상쇄돼 있었다) ③ `※` 개수 대조 |
