## 1. Executive Summary

한국 공공·금융 조달의 제안 담당자는 공고 하나를 받으면 **HWP 여섯 개, 200쪽**을 손으로 뜯는다. 마감까지 달력으로 9일이어도 공휴일을 빼면 **실질 5영업일**이고, 그 5일 동안 하는 일은 다섯이다 — 참가자격 판정 · 요구사항 조견표 작성 · 일정과 투입인력 설계 · 원가 산정 · 배점 역산. **첫 번째에서 틀리면 나머지 나흘이 통째로 무의미하다.**

**Solar for Bid는 회사 서류 한 묶음을 받아 조달 절차를 한 줄로 잇는다.** 회사 서류에서 자격을 뽑아 「회사 카드」를 만들고(S1), 그 카드로 나라장터 공고를 훑어 후보를 좁히고(S2), 후보의 첨부 HWP를 끌어와 Upstage Studio가 **읽고·가르고·뽑고**(S3), **참가자격을 대조해 낼 수 있는 것만 근거와 함께 추려 올리고**(S4), 요구사항 조견표를 **웹 체크리스트**로(S5) · WBS와 임계경로와 **M/M 예상 원가 추천**(S6) · 질의서 초안(S7) · 제출 체크리스트 검사와 보완요청(S8)을 만든다.

🔴 **S9 투찰은 하지 않는다.** 공동인증서와 지문인식보안토큰으로 잠긴 구간이다. **우리의 end는 「무엇을 언제 어디에 내야 하는지」와 예상비용으로 제안서 작성을 간접적으로 돕는 것**이고, 그 벽을 숨기지 않고 화면에 그린다 — 숨기면 현업 심사 첫 질문에 무너진다.

**Upstage에게 이 제품은** ① 자사 `Federal RFPs` 에이전트가 멈춘 세 자리 — **한국·회사·끝** — 를 채우는 것이고 ② 고객의 **52.5%가 금융권**이며 회사가 **2025-12 조달청 디지털서비스몰 첫 공급사**인, 이미 발을 들인 도메인이며 ③ 라이브러리 29개가 전부 「심사·처리하는 쪽」인 자리에서 **「서류를 내는 쪽」**의 두 번째 사례다.

**48시간이 증명하는 칸은 하나다** — 「회사 서류를 올리면 공고가 추려지고, 그중 한 건이 S3→S6까지 끊기지 않고 이어지고, 끝에 제출물 파일이 나온다」. S0·S7·S8은 경로만 그린다.

## 2. 기획 의도

### 2-1. 왜 이 문제인가 — 「이해」는 팔리고 있고, 「제출물」은 아무도 안 만든다

트랙 과제문은 *"goes beyond **'understanding'** documents to actually **'getting the work done.'**"* 라고 못 박았다.

조달에서 **understanding은 이미 상품이다.** 클라이원트(2023 창업·20억 투자)가 300+ 채널 공고 수집 → RFP 본문 자동 분석(150쪽 이상) → 요구사항 체크리스트 → Go/No-Go 근거 데이터를 3년째 판다. 올거나이즈는 RFP를 과거 제안 이력과 대조해 전략 리포트를 낸다.

**아무도 안 하는 것은 그 다음이다.** 확인된 국내외 16개 서비스 중:

| | 하는 곳 |
| --- | --- |
| 공고 알림·추천 | 다수 (나라장터·지투비플러스는 **무료**) |
| 투찰가 예측 | 6곳 (ML 학습, 수백만 건 데이터) |
| RFP 본문 분석·요약 | 3곳 |
| 요구사항 표 | 2~3곳 |
| 🔴 **WBS** | **0곳** |
| 🔴 **Critical Path** | **0곳** |
| 🔴 **문서 근거를 붙인 자격 미충족 선언** | **0곳** |

→ **기획 의도 한 줄**: *"조달 문서에서 「이해」는 이미 팔린다. 우리는 그 문서를 **제출할 수 있는 산출물**로 바꾸는 첫 자리를 만든다."*

### 2-3. 왜 지금인가 — 실호출로 열린 문 둘

이 기획은 두 달 전에는 못 세웠다. **오늘 02:20~02:30에 확인한 것 둘이 전제다.**

| 열린 것 | 값 |
| --- | --- |
| **나라장터 첨부가 인증 없이 받아진다** | `GET .../UntyAtchFile/downloadFile.do?bidPbancNo=&bidPbancOrd=&fileType=&fileSeq=` → HTTP 200, 쿠키·로그인·키 전부 불필요 |
| **Parse가 그 HWP를 그대로 받는다** | `file` 판정 `Hangul (Korean) Word Processor File 5.x`. **변환 단계가 통째로 없다** |

→ 이 둘이 만나서 **「회사 서류 한 묶음 → 공고 후보 → 문서 묶음 → 판정·산출물」**이 가능해졌다.
🔴 **공공데이터포털 API 키 — v1.2에서 위치가 바뀌었다.** 첨부(S3)는 여전히 키 없이 받아지고 메타는 공고문 HWP에서 뽑을 수 있다. 그러나 **S2 공고 목록 탐색은 키가 필요하다**(무인증 호출 = 코드 30). 키 승인이 늦으면 **목록을 미리 받아 캐시**하고 `meta.listSource: cached`로 화면에 밝힌다 — **키 승인 대기가 데모를 막지는 않지만, 라이브 탐색은 막는다.**

### 3-2. 타깃 — 한 사람, 그리고 당사자성

**타깃** — 중소 IT 컨설팅·SI 기업(임직원 50~100명)의 **제안 담당자**. 연 10~20건 검토, 그중 3~5건 응찰.

**페르소나** — 제안팀 과장. 금요일 오후 공고 하나를 받는다. 첨부 HWP 다섯, 합쳐 200쪽. 마감은 다음 주 목요일 14:00 인편. 달력으로 6일인데 공휴일이 껴서 **4영업일**. 월요일 아침까지 「낼까 말까」를 답해야 하는데, 그 답의 근거는 200쪽 안 어딘가에 있다.

#### 🔴 S4가 왜 두 갈래인가 — 「조건부」를 뺀 이유와 그 대가

**판정 어휘를 셋에서 둘로 줄였다.** 예전엔 `Go / No-Go / 조건부`였다. 조건부는 *"자격은 안 되는데 공동수급하면 된다"* 같은 **우회 경로를 추론하는 일**이라, 화면에도 세 번째 상태가 생기고 판정 로직에도 분기가 하나 더 붙는다. **남은 시간에 만들 수 있는 것이 아니다.** 뺐다.

그리고 **제외된 건은 화면에 올리지 않는다.** 사람이 볼 것은 추천 목록뿐이고, 게이트는 거기에만 건다 — 「이건 하겠다(응찰) / 이건 안 하겠다」. **응찰을 고른 건만 S5로 내려간다.** 안 고른 건은 거기서 끝이다.

> [!error] 🔴 그래서 생기는 위험 하나 — 그리고 그것을 막는 규칙
> 제외된 건은 **화면에서 사라진다.** 사람이 검증할 기회가 없다는 뜻이다.
> 그런데 우리 추출은 장문 F1이 41.3/63.2다 — **참가자격 조항을 못 읽는 일이 반드시 생긴다.** 못 읽은 것을 제외로 처리하면, **우리 OCR 실패가 회사의 사업 기회를 조용히 지운다.**
> 조달에서 이 둘은 값이 다르다 — 놓친 공고는 되찾을 수 없고, 잘못 올라온 공고는 사람이 30초에 거른다.
> → **규칙: 제외는 근거가 있을 때만 한다.** 자격 항목의 미충족을 **쪽 번호와 함께** 확인했을 때만 뺀다. 못 읽은 것(`[확인필요]`)은 **추천에 넣고 「미확인 N건」을 단다.** 가점 미충족도 제외 사유가 아니다 — 점수만 깎이지 참가는 된다.

#### 🔴 분모를 보여준다 — 「127건 중 3건」

추천 3건만 화면에 뜨면 **우리가 무엇을 했는지 안 보인다.** 그래서 스크리닝 응답에 `scanned · excluded · shortlisted`를 담고, **제외 사유 표본도 근거와 함께** 담는다(화면에는 접어 둔다). 심사에서 *"나머지는 왜 뺐냐"*가 나오면 그 자리를 편다 — 이 제품이 가장 강한 지점이다.

→ 목록 응답 규격은 `04_계약/screening.envelope.json`, 상세 1건은 `04_계약/factsheet.envelope.json`. **둘은 다른 모양이다.**

| 8 | 🔴 **공동수급협정서는 3단계**(대표사 작성 → 구성사 승인 → 대표사 제출). 대표사가 최종 제출을 안 눌러 무효되는 사고가 반복된다. **입찰서를 먼저 내면 협정서를 못 고친다** | 제출 체크리스트 · 임계경로 |
| 9 | **입찰참가자격 등록에 시간이 걸린다.** 공고 발견 후 시작하면 마감 전 승인이 안 난다 | 임계경로 경로 A의 선행 작업 |

🔴 **함정 1이 이 제품의 가장 강한 한 문장이다.** 「공고서가 제안요청서를 이긴다」는 조달 실무의 기본인데, 사람은 200쪽을 두 번 읽지 못해 놓친다. **우리는 두 문서를 같은 스키마로 읽으므로 불일치가 기계적으로 드러난다.**

### 4-3. 단계별 Studio 매핑 — `Studio must power the core`

| 단계 | Studio 노드 | 우리 코드 | 출력 |

🔴 **`Validate` 노드를 S4에서 시도한다.** PDF p13이 공식 노드로 싣고 있고(*"Validate accuracy of extraction results"*) **공개 에이전트 29개 중 사용이 0개**다. 우리 검산(요구사항 ID 대조·배점 소계 = 항목합)이 정확히 그 용도다. 🔴 **툴바에 없으면 Node로 같은 검산을 한다 — 전제로 삼지 않는다.**

### 4-7. Federal RFPs가 멈춘 자리 — 우리 좌표

Upstage 자신의 RFP 에이전트를 공개 API로 재구성한 것:

```
Parse (document-parse-260128 · mode=auto · ocrMode=force · coordinates=true
       outputFormats=[html,text] · base64Encoding=[figure] · mergeMultipageTables=false)
 └─ Classify-1 ─ 4갈래: negotiated_rfp / simplified_rfq / task_order / idiq_base_vehicle
      └─ Extract ─ categorySchemaMapping으로 갈래별 스키마 4벌 (각 ~40필드)
           └─ Instruct: prep_kit    ─ compliance_matrix + submission_checklist + bid_readiness_flags
                └─ Instruct: risk_triage ─ 조항 위험 분류 + 상위 3~5건
```

| 없는 것 | 근거 | Solar for Bid |
| --- | --- | --- |
| **한국** | `language:"en"`. FAR·Section L/M·SF-1449·CLIN·NAICS 어휘. HWP 개념 없음 | 나라장터·협상에의한계약·요구사항조견표·기술90:가격10·인편접수 어휘. **HWP/HWPX 직접** |
| **회사** | Extract ~40필드가 **전부 공고 쪽**. 우리 회사가 충족하는지 대조하지 않는다 | 회사 카드(회사 서류를 Parse한 것)와 **기계 대조** → 미충족을 페이지 인용과 함께 선언 |
| **외부 연동** | **없다.** 사람이 파일을 올려야 시작한다 | **나라장터 자동 수집** |
| **끝** | `prep_kit`(분석)에서 멈춘다. WBS·임계경로·원가·파일 없음 | **웹 체크리스트 + WBS·임계경로 파일 + M/M 추천 + 제출 보완요청** |

> [!error] 🔴 여기서 **베낄 것**과 **자랑하면 안 되는 것**
> **베낀다**: `ocrMode:"force"`(회사 자신이 RFP에 OCR을 강제한다) · Classify 설명문 3단 작법(Distinguishing → KEY NEGATIVE → KEY DISTINCTION) · Extract 필드 정규화 규칙 · **Instruct가 Instruct를 받는 체이닝**
> 🔴 **자랑하지 않는다 — 노드 개수.** 공개 API 플래그는 노드 **종류**(최대 4종)를 세는 값이지 개수가 아니다. **실물 캔버스 p23이 16노드·7갈래**이고 **우리 14노드는 그보다 적다.** 개수로 말하면 그 자리에서 반증된다.

### 5-4. Agents API 호출 흐름 — **폴링**

```
Flutter ──공고번호──▶ Node ──[0] fileSeq 1..N 수집 (키 불필요) ──▶ HWP 묶음
                     Node ──[1] 파일 업로드 ──────────────────▶ file_id
                     Node ──[2] Job 생성 (agent_id + config_id) ▶ job_id
                     Node ──[3] Job 조회 2~5s ─────────────────▶ status · 결과 · confidence
```

🔴 **webhook 없음 — 폴링 확정.** 처리는 *"보통 분 단위"*. **실패한 실행은 과금되지 않는다** → 재시도 단순화. Config 버전은 데모 전날 고정하고 그 뒤 캔버스를 건드리지 않는다.

### 5-5. 판정 어휘와 검산 — 우리가 쓰는 유일한 「규율」

| 층 | 규칙 |
| --- | --- |
| **판정 어휘** | 자격은 `충족 / 미충족 / [확인필요]` 셋뿐. 값은 `grounded / not-in-document / mismatch` |
| **근거 강제** | 모든 grounded 판정에 **페이지 번호**. Extract가 좌표를 주므로 원문 대조가 가능하다 |
| **지어내지 않기** | 회사 카드에 없는 실적·자격을 만들지 않는다 → `[확인필요]`. 법령을 **해석하지 않는다**(조문 이름만 그대로 옮긴다) |
| **confidence 분기** | Extract `low` → 화면에 ⚠ + 사람 확인. `high`만 자동 진행 |
| 🔴 **검산 셋** | ① 조견표 행 수 = 목록표 ID 수(**ID 대조**까지) ② **배점 소계 = 항목합**(총합만 보면 못 잡는다 — 실물에서 (10) vs 11, (10) vs 9가 상쇄돼 있었다) ③ `※` 개수 대조 |

## 12. BM과 확장 — 48시간이 증명한 것만

| | |
| --- | --- |
| **누가 돈 내나** | ① **중소 SI·컨설팅 기업** — 연 10~20건 검토에 건당 3~5일. 제안 담당자 인건비가 비용이다 ② **Upstage의 금융 고객** — 은행·보험사도 IT 조달의 **발주 쪽**에서 같은 문서를 본다 `[확인필요]` ③ 조달 정보 서비스(클라이원트 등)에 **산출물 레이어로 얹기** |
| **단위 문장** | *"공고 한 건당 제안 착수 준비 시간을 3~5일에서 N시간으로 줄인다."* — **N은 비운다.** 48시간이 재는 것은 시간이 아니라 **정확도**다 |
| **Upstage가 얻는 것** | ① `Federal RFPs`의 **한국판 수요 신호** — 라이브러리에 조달 카테고리가 0개다 ② HWP 문서군의 실데이터 ③ **「서류를 내는 쪽」** 두 번째 사례 |
| **48시간이 증명하는 칸** | **「공고 한 건에서 요구사항 N건을 몇 % 정확히 뽑아 제출 가능한 파일로 만드는가」 — 이것 하나.** 나머지는 추정. 발표에서 *"저희가 보인 건 이 한 칸입니다"* |
| **로드맵** | v1 회사 1개 · 응찰 1건 → v2 사전규격 연계(S0)·여러 회사 → v3 낙찰 사후 추적·기관 카드 → v4 제안서 초안(그때는 조견표가 근거가 된다) |
