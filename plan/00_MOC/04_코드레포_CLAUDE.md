## 🔴 파트너 제품 — 쓰는 게 필수다. 다시 만들면 실격

**적용 조건**: 브리핑이 **파트너 제품 사용을 요구한 트랙**일 때만 이 절이 돈다. 다른 트랙이면 건너뛴다 — 지우지는 마라.
**우리 트랙**: `[8/21 22:25 트랙 확정 후 이름을 적는다]` — 🔴 **비어 있으면 이 절이 적용되는지 아직 모른다는 뜻이다. 그 상태로 파서를 짜지 마라.**

Upstage 트랙 브리핑 원문(덱 p.27):

```
*Upstage Studio must power the core document-processing stages.
```

| 하는 짓 | 판정 |
| --- | --- |
| Studio 노드를 **호출해서 쓴다** (REST API · webhook) | ✅ **필수.** 안 쓰면 요건 위반이고 배점 30을 백지로 낸다 |
| Studio가 하는 일을 **직접 구현한다** — 자체 파서·추출기·분류기·OCR 파이프라인 | 🔴 **즉사.** 이미 제품인 걸 다시 만들면서 30점까지 스스로 버린다 |

🔴 **당신이 실제로 하려 할 일이 이것이다** — *"PDF 파싱은 라이브러리 하나면 되는데 API 왕복보다 빠르다."* `pdf-parse`·`pdfjs`·`tesseract`·직접 짠 정규식 추출기·직접 짠 분류 프롬프트. **전부 금지다.** 느린 게 문제가 아니라 **그게 실격 사유**다.
**문서를 텍스트로 만들고 · 분류하고 · 필드를 뽑고 · 요약/판단하는 경로는 Studio를 통과해야 한다.**
배점 원문: `Upstage Technology Implementation (30) How deeply the team leveraged Upstage Studio and its APIs — agent composition, external integrations, and the difficulty and accuracy of the implementation.`

**쓸 수 있는 노드**: `Parse` · `Classify` · `Extract` · `Instruct`

🔴 **`Validate`를 전제로 코드를 짜지 마라.** 덱 p.13 기능 소개에는 5번째 노드로 있지만 **Studio 화면의 단계 추가 툴바에도, 브리핑의 조합 문구에도 없다.** 없다고 단정도 하지 마라 — 화면에서 먼저 확인하고 쓴다.

🔴 **Solar 모델은 confidence score를 안 준다.** Classify 노드 설정 패널 문구 그대로: *"Solar 모델은 confidence score 기능을 아직 제공하지 않습니다."*

## 🔴 계약 — 이 프로젝트에서 가장 중요한 칸

`front/`와 `backend/`가 갈려 있다. **접점은 API 하나뿐이고, 터지면 거기서 터진다.**
수평으로 나눈 팀이 새벽 4시에 "두 덩어리가 안 붙는다"를 발견하는 것이 가장 흔한 실패다.

API 스키마: `[경로 — 8/22 00:30에 정한다]`

🔴 **8/22 04:00 동결.** 그 뒤로 바꾸려면 **둘이 같이** 바꾼다.
한쪽만 바꾸면 다른 쪽이 즉시 깨진다. **그게 의도다.**

동결 전까지 정할 것 — 엔드포인트 목록 · 요청/응답 필드명 · 타입 · 에러 형식 · 🔴 **라이브/캐시 스위치**.
**이름을 지금 정하라.** 나중에 바꾸면 양쪽이 깨진다.
🔴 **라이브/캐시는 동결 항목이다.** 파트너 API 응답을 라이브로 받든 캐시에서 읽든 **프론트가 보는 모양이 같아야 한다.** 04:00에 이걸 안 박으면 8/23 데모 중 전환이 물리적으로 불가능해진다 → 위 「크레딧」.

## 「경계」를 나누는 방식 넷 — 8/21 밤에 하나 고른다

> [!success] ✅ 2026-08-21 확정 — **D안으로 시작해 A안(수평)으로 갈라진다**
> 팀이 정한 폴더 구조가 `front` / `backend`이고 담당도 **이용현 프론트 · 길정민 백엔드**다. 이건 **A안(수평 분할)**이다.
> [[04_사전결정]] D-4에는 *"D안 → (b) 수직 분할"*로 적혀 있었는데 **갈라진 뒤가 B가 아니라 A**다. 앞부분(D안 — 00:00~04:00 둘이 같이 뼈대)은 그대로다.
>
> 🔴 **이 차이가 계약의 무게를 바꾼다.** 아래 표대로 B안은 *"아예 안 겹치게. 계약이 덜 중요해진다"*지만 **A안은 *"(a) API 스키마 동결이 필수. 접점이 그것뿐이라 거기서 다 터진다"***다.
> → **8/22 04:00 동결이 「하면 좋은 것」이 아니라 「안 하면 터지는 것」이 됐다.** [[12_뼈대설계]] 출력 C(계약 — 엔드포인트·필드명·타입을 이름까지)가 이 팀에서 가장 중요한 칸이다.
>
> ⚠️ A안의 알려진 위험 둘도 그대로 온다 — **한쪽이 막히면 다른 쪽이 논다** · **통합이 마지막에 몰린다.** 뼈대 구간(00:00~04:00)에 **양쪽이 붙는 것을 한 번 확인**해두면 둘 다 크게 줄어든다.

> [!important] 이게 [[04_사전결정]] D-4보다 **상위 결정**이다
> 어떻게 나누느냐가 정해져야 **계약 방식(D-4)이 따라온다.** 순서를 뒤집으면 안 된다.

### A. 수평 분할 — 프론트 / 백엔드

가장 흔하고, 각자 잘하는 쪽을 맡는다.

| --- | --- |
| 좋은 점 | 스택이 안 겹친다. 에이전트가 서로의 코드를 볼 일이 없다 |
| 🔴 나쁜 점 | **프론트가 백엔드 완성을 기다린다.** 한쪽이 막히면 다른 쪽이 논다 |
| 🔴 나쁜 점 | **통합이 마지막에 몰린다.** 새벽 4시에 안 붙는 걸 발견하는 전형적 경로 |
| D-4 계약 | **(a) API 스키마 동결이 필수.** 접점이 그것뿐이라 거기서 다 터진다 |

### 🟢 D. 뼈대 먼저 → 갈라지기 *(추천)*

**처음 4~6시간은 둘이 같은 것을 만들고**, 그다음 A나 B로 갈라진다.

같이 만드는 것: 스캐폴드 · 데이터 모델 · 공통 레이아웃 · 배포 파이프라인 · **API 스키마**

| | |
| --- | --- |
| 🟢 좋은 점 | **공통 코드 충돌이 원천 제거된다.** B안의 유일한 약점을 없앤다 |
| 🟢 좋은 점 | **계약이 자연스럽게 생긴다.** 둘이 같이 만들었으니 둘 다 안다 |
| 🟢 좋은 점 | **통합 위험이 앞으로 당겨진다** — 새벽 4시가 아니라 첫날 밤에 |
| 나쁜 점 | 초반 병렬성을 잃는다. 4~6시간 동안 2명이 1명치 |

**그 손실이 통합 사고 한 번보다 싸다.** 그리고 스캐폴드를 대회 전에 만들어두면 이 구간이 통째로 줄어든다.

```
8/22 00:00~04:00  둘이 같이 — 스캐폴드·모델·계약
8/22 04:00        🔴 계약 동결
8/22 04:00~       B안으로 갈라짐
```

### 어떻게 고르나

| 조건 | 고를 것 |
| --- | --- |
| 스캐폴드를 대회 전에 만들어 갔다 | **D → B.** 뼈대 구간이 짧아져 손실이 거의 없다 |
| 스캐폴드가 없다 | **D → B.** 어차피 뼈대를 만들어야 한다 |
| 둘의 스택이 완전히 갈린다 (한 명은 프론트만, 한 명은 백만) | **A.** 단 계약 동결을 반드시 |
| 기능이 하나뿐이다 | **C만 남는다.** 나눌 게 없다 |

🔴 **기능이 3개면 B가 안 나눠진다.** 2명이 3기능을 맡으면 한 명이 둘을 갖는다 — 그 사람이 병목이 된다. **기능 수와 사람 수를 맞추는 것도 판단에 들어간다** → [[03_핵심기능]]
