# 핵심기능

> [!important] 기능은 줄이는 쪽이 거의 항상 옳다
> 하나가 확실히 도는 게 셋이 반쯤 도는 것보다 항상 낫다. 특히 **Expo에서 3시간 동안 개발자들에게 보여야 한다면** 더 그렇다 — 그들은 **반쯤 도는 걸 즉시 알아본다** → [[02_동료해커]]

## 이 팀의 실현 가능 범위 — 기능을 정하기 전에 읽는다

개발자 2인이 **각자 28시간**([[02_팀과_제약]] 시간 예산 표의 개발 3행 합계 8+12+8 — 데모 준비 4시간은 뺀 값), 무박 후반 효율 감소를 반영하면 **유효 45 person-hours**다. **이 45가 기능을 만드는 전부다.**

> [!error] 🔴 기획자와 디자이너를 여기에 더하지 마라 — [[04_사전결정]] D-7 ✅확정
> D-7이 기획자를 **개발자 크리티컬 패스 밖**에 뒀다. 기여는 **데모 하네스**로 좁혀져 있다 — 시드 데이터 · 리셋 버튼 · 폴백 녹화본 · 목업 전환 스위치 · 데모 경로 스모크 러너. 디자이너는 피그마다.
> 둘 다 **기능을 만드는 시간이 아니라 개발자가 안 쓸 시간을 대신 쓰는 차선**이다. 45에 더하면 하드룰 2(28시간)를 **넘긴 걸 모르고 넘긴다.**
>
> D-7의 원래 취지가 여기 있다 — *"기능 하나 더 붙이는 게 최악이다."* 기획자가 프론트를 보조하면 코드는 늘지만 **막혔을 때 개발자를 부르고**, 그 인터럽트가 45를 깎는다. 차선으로 좁히면 안 부른다.

### AI가 몇 배를 만들어주나

개발자 둘 다 Claude Max·Codex Max를 풀로 돌린다. 에이전트 코딩은 **코드 작성**을 3~4배로 만든다. 그런데 개발 시간은 코드 작성만이 아니다.

```
코드 작성 50%  ·  디버깅·통합 35%  ·  환경·배포 15%
```

**AI는 앞의 50%만 줄인다.** 두 시스템이 안 붙는 이유를 찾는 시간, API가 예상과 다르게 응답하는 시간, 배포가 로컬과 다르게 도는 시간은 에이전트가 못 줄인다.

→ **전체 배속은 1.6~2배.** 4배가 아니다. 유효 45 × 1.8 ≈ **일반 팀 기준 80 person-hours어치**.
일반적인 강한 팀이 40~50을 뽑으니, **좋은 팀이 이틀 걸려 만들 걸 만들 수 있다** — 프로토타입이 아니라 **완결된 제품 한 조각**이다.

> [!note]- 위 분해는 측정값이 아니라 추정이다
> 그린필드 프로젝트의 통상적 비율로 잡았다. 팀의 실제 비율이 다르면 배속도 달라진다. **중요한 건 배수가 아니라 "AI가 못 줄이는 절반이 있다"는 구조다.**

### 티어

| 티어 | 산출물 | 판단 |
| --- | --- | --- |
| **안전** (~40ph) | 배포된 URL · 핵심 플로우 **1개**가 끝까지 실제 동작 · 진짜 백엔드+DB(목업 아님) · LLM API 1개 실연동 · 디자이너 손 탄 UI · 시드 데이터와 리셋 | 거의 확실히 됨 |
| **목표** (~70ph) | 위 + 핵심 플로우 **2~3개** + **기술적으로 어려운 것 1개**(RAG·에이전트 루프·문서 파싱·실시간 스트리밍 중 하나) + 합성이 아닌 **실제 데이터**로 동작 + n을 밝힌 자체 측정 수치 1개 | **이 팀이면 현실적** |
| **무리** | 모바일 네이티브 · 실시간 협업 동기화 · 모델 학습 · 인프라 운영 · 로그인/회원가입 | 손대면 깨짐 → [[03_금지목록]] |

**"기술적으로 어려운 것 1개"를 빼지 말 것.** 심사의 *기술적 도전*과 *독창성*이 거기서 갈리는데, AI 권장 대회라 API 호출 조합은 전 팀이 해온다.

> [!error] 🔴 이 팀이 질 가장 큰 이유는 시간 부족이 아니다
> **코드가 싸지면 병목이 "무엇을 만들지"로 옮겨간다.** 만들기 쉬우니 기능을 더 넣고 싶어지고, 그러면 통합 지옥에 들어간다.
> 가장 그럴듯한 패배 시나리오는 **못 만들어서**가 아니라 **너무 많이 만들어서 아무것도 3시간 동안 안정적으로 안 도는 것**이다.
> → 아래 "최대 3개"는 AI 쓰는 팀에서 **느슨해지는 게 아니라 더 엄격해진다.** 그리고 코드베이스가 갈라지는 문제는 [[04_사전결정]] D-4에서 미리 막는다.

## 근거 — 이 기능을 왜 만드나

> [!tip] 여기는 [[01_문제정의]]의 근거표와 **묻는 것이 다르다** — 같은 인용을 복붙하지 마라
> 문제정의는 *"이 문제가 진짜인가"* 를 묻는다. 여기는 *"왜 **이** 기능인가"* 를 묻는다.
> 문제가 진짜인 것과 이 기능이 그 문제의 답인 것은 **다른 주장**이고, [[03_회의론자]]는 둘을 따로 찌른다.

| 기능# | 등급 | 신뢰 | 인용 (그대로) | 누가 | 시각 | 이 말을 못 들었어도 만들었나 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | | | | | | |
| 2 | | | | | | |
| 3 | | | | | | |

🔴 **마지막 칸이 이 표의 전부다.** *"못 들었어도 만들었다"* 면 그 인용은 **근거가 아니라 장식**이다. 같은 브리핑을 읽은 60팀이 도착하는 자리라는 뜻이고, 인용을 붙여도 평범함은 안 없어진다 → [[11_평범한답]]
*"이 말을 듣고 방향을 바꿨다"* 가 나오는 기능이 **하나도 없으면 워크숍을 헛들은 것이다.** 22:00 전에 알아채야 고칠 시간이 있다.

🔴 **「누가」가 전부 `팀`·`우`면 그 근거는 우리끼리 만든 것이다.** 최소 한 줄은 `담`·`엔`이거나 **파트너 제품을 실제로 쓰는 사람**이어야 한다.

**등급** 🔴새 사실 / 🔴문서 뒤집기 / ⚠️문서와 모순 / 🔵회피 · **신뢰** ✅확실 / ⚠️재확인 · **누가** 담·엔·멘·스·팀·우 (모르면 `?`)
**앞 4칸**(등급·신뢰·인용·누가)이 [[10_발화채집]] A절 출력 그대로 — 옮겨 적지 말고 붙여넣는다. ⚠️ **채집 출력엔 `시각`이 없다** — `시각`과 맨 끝 칸은 손으로 채운다. 5칸을 통째로 붙이면 칸이 밀린다.

## 하나만 남긴다면

```
[채우기]
```

이걸 정해두면 시간이 모자랄 때(반드시 모자란다) 판단이 빠르다.

## 안 만드는 것 — 명시

심사에서 "이건 왜 없냐"에 답하기 위한 목록. **못 한 게 아니라 안 한 것**으로 만든다.

| 안 만든 것 | 이유 | 근거 인용 — 파트너가 원하지 않는다고 **말한** 것 |
| --- | --- | --- |
| 로그인·회원가입 | 데모 점수에 기여하지 않고 시간을 가장 많이 먹는다 | (우리 판단) |
| `[채우기]` | | |

**셋째 칸이 채워진 줄이 가장 세다.** *"안 만들었습니다"* 보다 *"안 원한다고 하셔서 뺐습니다"* 가 훨씬 강하다 — 파트너 말을 들었다는 증거가 되고, 심사에서 「왜 없냐」를 **질문 자체로 성립 안 하게** 만든다. → [[06_트랙해부]] 「파트너가 원하지 않는 것」에서 옮겨온다
