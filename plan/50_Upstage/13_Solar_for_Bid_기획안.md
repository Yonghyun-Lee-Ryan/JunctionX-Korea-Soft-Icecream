## 1. 🔴 Upstage 자신의 RFP 에이전트가 멈춘 자리 — 이 기획의 출발점

`Federal RFPs` 전체 설정을 공개 API로 받아 재구성한 파이프라인이다.

```
Parse  (document-parse-260128 · mode=auto · ocrMode=force · coordinates=true
        outputFormats=[html,text] · base64Encoding=[figure] · chartRecognition=false)
  └─ Classify-1  ─ 4갈래: negotiated_rfp / simplified_rfq / task_order / idiq_base_vehicle
       └─ Extract  ─ categorySchemaMapping으로 갈래별 스키마 4벌 (각 ~40필드
                     + 중첩배열 clins · proposal_volumes · evaluation_factors.subfactors · clauses)
            └─ Instruct: prep_kit      ─ compliance_matrix + submission_checklist
            │                            + bid_readiness_flags + source_clauses
            └─ Instruct: risk_triage   ─ 조항 위험 분류 + 상위 3~5건
```

**여기서 배울 것 (그대로 베낀다)**
- `ocrMode: "force"` — Upstage 자신이 RFP에 OCR을 **강제**한다. 스캔 섞인 조달문서 대응의 정답
- Classify 설명문 작법 — **Distinguishing features → KEY NEGATIVE → KEY DISTINCTION vs X** 3단
- Extract 필드 작법 — `"Exactly one word: 'services','product','hybrid'"` · `"ISO YYYY-MM-DD"` · `"raw number, no $ or commas"` · `"Fallback ladder: (1)… (2)…"` · `"empty if not stated"`
- **Instruct가 Instruct를 받는다** — `connectionMapping`에 `risk_triage ← prep_kit ← extract`. 노드 체이닝이 공식 지원된다

**🔴 여기서 멈춘 것 (우리 자리)**

| 없는 것 | 근거 | Solar for Bid |
|---|---|---|
| **한국이 없다** | `language: "en"`, FAR·Section L/M·SF-1449·CLIN·NAICS·set-aside·IDIQ 어휘. HWP 개념 자체가 없다 | 나라장터·협상에의한계약·요구사항조견표·기술90:가격10·인편접수·정규직비율 어휘. **HWP를 그대로 받는다** |
| **회사가 없다** | Extract 필드 ~40개가 **전부 공고 쪽**이다. `bid_readiness_flags`에 set-aside eligibility가 있지만 *우리 회사가 그걸 충족하는지* 대조하지 않는다 | 회사 프로필과 **기계 대조**해 미충족을 페이지 인용과 함께 선언 |
| **일이 안 끝난다** | 출력이 `prep_kit`(분석 결과)에서 멈춘다. **WBS도, 임계경로도, 원가도, 파일도 없다** | **파일 네 개**가 나온다 |
| **아무도 안 쓴다** | copy 1 · like 0 | — |

> **부스 문장**: *"라이브러리에서 Federal RFPs를 봤습니다. 저희가 하려던 것과 파이프라인이 거의 같더군요. 그런데 복사가 1회입니다. 세 가지가 없어서라고 읽었습니다 — 한국, 회사, 그리고 끝."*

## 3. 문제와 당사자

**당사자** — 중소 IT 컨설팅·SI 기업의 **제안 담당자**. (팀 기획자 팀 기획자가 실제로 하는 일이다. 지금 5건을 손으로 처리 중이다.)

**사고 장면 [관찰]** — 나라장터에 공고가 뜬다. 첨부는 HWP 여섯 개, 합쳐 200쪽. 마감까지 달력으로 9일인데 광복절·대체공휴일이 껴서 **실질 5영업일**이다. 그 5일 동안 사람이 하는 일:
1. 참가자격 여섯 줄을 읽고 우리가 되는지 판단한다 — 🔴 **여기서 틀리면 나머지 5일이 통째로 무의미하다.** 실물 사고: 금융권 RFP에서 「최근 3년 동일 업권 대형구축 PMO 실적」이 가점인 줄 알았는데 **참가자격**이었다
2. 요구사항 151건을 엑셀로 옮겨 조견표를 만든다 — **발주처가 요구하는 실제 제출물이다. 20부를 출력해서 낸다**
3. 과업내용서를 읽고 일정과 투입인력을 짠다
4. 원가를 세운다
5. 배점표를 뜯어 커트라인을 역산하고 분량을 배분한다

**돈·시간·리스크** — 시간: 1~5가 사람 손으로 3~5일. 리스크: ①에서 틀리면 제안 자체가 무효. 실물: 제안서 3부 + 요약서 20부 + **조견표 20부 = 43부** 출력, 인편 접수.

> ⚠️ **정직하게**: 이 문제 문장은 팀 기획자의 **[관찰]**이고, 외부 당사자 인터뷰는 0건이다. 8/22 낮 창구에서 채우거나, 못 채우면 발표에서 먼저 밝힌다 → 10절 R3

## 4. 산출물 넷 — 「각 분야 용어로 호환되게」

🔴 **이 절이 이 기획의 심장이다.** 확인된 16개 서비스 중 ③④를 내는 곳은 **0곳**이고, Upstage의 Federal RFPs에도 없다.

### 4-1. 요구사항 조견표 — 제안팀 어휘 (제출물)

| 요구사항 ID | 분류 | 요구사항 명칭 | 세부내용 | **※ 단서** | 근거 p | **수용 여부** | 대응 제안서 목차 |
|---|---|---|---|---|---|---|---|
| CSR-017 | 공통 | … | … | ※ 단, 기존 시스템은 제외 | p47 | 수용 / 부분수용 / 해당없음 | Ⅲ-나-2 |

- 열 구조는 볼트 실물([[06_요구사항_조견표_제출본]] 54건 · 공공기관 B 151건)에서 그대로 가져온다

### 4-3. Critical Path — 일정 어휘

- 선후행 → **ES/EF/LS/LF · Total Float · 임계경로**

### 4-4. 예상 원가 — 견적 어휘 (🔴 투찰가가 **아니다**)

> [!error] 🔴 이 칸의 경계선
> **「적정 투찰가를 계산해 드립니다」는 하지 않는다.** ① 문서 처리가 아니라 30점에 기여 0 ② 최소 6곳이 수백만 건 낙찰 데이터로 학습한 예측을 이미 판다 ③ 「출처 없는 숫자 금지」 하드룰에 정면으로 걸린다.
> 우리가 하는 것은 둘뿐이다 — **(a) 공고에 적힌 값을 페이지 인용과 함께 옮긴다** (추정가격·배정예산·낙찰하한율·가격평가 산식·계약체결방법) **(b) WBS에서 나온 공수로 원가를 세운다.**

| 항목 | 값 | 근거 |
|---|---|---|
| 추정가격 / 배정예산 | 공고에서 추출 | 공고문 p3 |
| 낙찰하한율 · 가격평가 산식 | 공고에서 추출 | 공고문 p7 |
| **WBS 총 공수** | 4-2에서 합산 | 자동 |
| **원가 추정** | 공수 × 등급별 단가 `[확인필요: SW기술자 평균임금 최신본]` | 계산 |
| 예산 대비 | 원가 / 배정예산 = N% | 계산 |

## 5. Studio 파이프라인 설계 — `studio.upstage.ai/agents`에서 지금 만들 것

### 5-1. 캔버스 그래프 (14노드)

> [!error] 🔴 노드 **개수**로 자랑하지 않는다 — 그 자리에서 반증된다
> 공개 API의 `documentParseEnabled` 류 플래그는 노드 **종류**(최대 4종)를 세는 것이지 노드 개수가 아니다. **실물 캔버스는 이미 더 깊다** — PDF p23 「식약처 의약품 허가 여부 진단」이 **16노드 · 7갈래**다(p22는 6노드·2갈래). **우리 14노드는 그보다 적다.**
> 깊이는 이렇게 말한다 — ① **Split ON**(공개 29개 중 사용 0) ② **`merge_multipage_tables: true`**(Federal RFPs는 false) ③ **Instruct 4단 체인**(Federal RFPs는 2단) ④ 🔴 **문서군 두 개를 맞댄다** — 공개 29개도 Federal RFPs도 전부 *한 종류 문서*만 본다. 우리는 **공고 문서 ↔ 회사 프로필**을 대조한다 ⑤ Extract confidence low/high 게이팅

```
Parse ─ mode=auto · ocrMode=force · coordinates=true · outputFormats=[html,text]
 │       base64Encoding=[figure] · mergeMultipageTables=TRUE   ← Federal RFPs와 다른 유일한 칸
 │       (한국 RFP는 요구사항 표가 수십 쪽에 걸쳐 이어진다)
 │
 └─ Classify-doc-kind ─ Split 활성화 ON ─ 6갈래 + others
      ├─ ntce_notice   → Extract-공고문     → ┐
      ├─ rfp_main      → Extract-제안요청서  → │
      ├─ sow_task      → Extract-과업내용서  → ├→ Instruct-1  자격판정
      ├─ req_spec      → Extract-요구사항    → │   (회사 프로필 ↔ 참가자격, 충족/미충족/[확인필요])
      ├─ eval_sheet    → Extract-배점표      → │        ↓
      ├─ form_annex    → Extract-제출서식    → ┘   Instruct-2  조견표행 생성 (※ 단서 보존·합계 검산)
      └─ others        → 「분석 대상 아님」            ↓
                                              Instruct-3  WBS 전개 (작업패키지·선후행·산출물·요구사항ID 역참조)
                                                   ↓
                                              Instruct-4  임계경로 + 제출 체크리스트
```

🔴 **Split을 켜는 것이 Federal RFPs와 갈리는 지점이다.** 그들은 껐다(문서 1건 = 유형 1개). 한국 조달은 **한 건에 문서 여섯이 딸려 오거나 합본 스캔으로 온다** — p17 `Auto-splitting — Separate files with bundled documents into sub-documents`가 정확히 이 입력을 위한 기능이다.

### 5-2. Classify 스키마 — Upstage 작법(Distinguishing / KEY NEGATIVE / KEY DISTINCTION) 이식

| 레이블 | 설명 칸에 그대로 붙여넣을 문장 |
|---|---|
| `ntce_notice` | **입찰공고문.** 식별 특징: 상단에 「입찰공고」 또는 「◯◯ 공고 제YYYY-NN호」, 공고번호, 입찰방식·계약방법·낙찰자결정방법·입찰서 제출마감일시·개찰일시·추정가격 또는 기초금액이 한 표에 모여 있다. 분량 1~5쪽. **이것이 아님:** 과업 요구를 장·절로 서술하면 `rfp_main`, 요구사항이 ID 표로 나열되면 `req_spec`. **경계:** 공고문은 「언제·어떻게·누가 낼 수 있나」만 말하고 「무엇을 만드나」는 말하지 않는다. |
| `rfp_main` | **제안요청서 본문.** 식별 특징: 「제안요청서」 표제, 장·절 목차(Ⅰ 사업개요 / Ⅱ 사업내용 / Ⅲ 제안서 작성요령 / Ⅳ 제안 안내사항 / Ⅴ 제안 가격), 사업 배경·목적·범위·기간·예산 서술, 제안서 목차 지정, 분량·부수·양식 규정, **금지 표현 열거**. 15~200쪽. **이것이 아님:** ID 표만 있으면 `req_spec`, 배점만 있으면 `eval_sheet`. **경계:** 제안요청서는 서술문, 요구사항정의서는 표다. 한 파일에 둘 다 있으면 Split으로 가른다. |
| `sow_task` | **과업내용서·과업지시서·과업설명서.** 식별 특징: 해당 표제, 과업을 단계·영역별로 서술, **산출물 목록과 제출 시기**, 투입인력 등급·기간, 검수 기준. **이것이 아님:** 제안 작성·평가·제출을 다루면 `rfp_main`. **경계:** 과업내용서는 「낙찰 후 무엇을 하나」, 제안요청서는 「낙찰되려면 무엇을 내나」. **WBS의 원재료가 이 갈래다.** |
| `req_spec` | **요구사항 정의서.** 식별 특징: **요구사항 고유번호 체계**(SFR-·PFR-·TER-·SER-·COR-·PMR-·CSR-·PAR-·QUR-·ECR- 등 접두사 + 일련번호)와 「분류 / 명칭 / 정의 / 세부내용」 열. 한 행이 한 요구사항, 수십~수백 행. 세부내용에 **`※`로 시작하는 단서·예외**가 자주 붙는다. **이것이 아님:** 배점·평가항목 표는 `eval_sheet`, 서술식 과업은 `sow_task`. **경계:** 이 갈래가 조견표의 원재료다 — 행 단위로 빠짐없이, **`※`를 잃으면 요구를 반대로 읽는다.** |
| `eval_sheet` | **제안서 평가표·배점표.** 식별 특징: 「평가항목 / 배점 / 평가방법」 열, 정성·정량 구분, 기술·가격 비율(예: 기술 90 / 가격 10), 등급 환산표(S·A·B·C·D), 기술평가 하한(예: 85% 미만 탈락), 동점 처리. **이것이 아님:** 요구사항 ID 표는 `req_spec`. **경계:** **배점 합계가 100 또는 90+10으로 떨어지는지가 검산 지점이다** — 표기 배점과 항목 합이 어긋나는 실물이 있다. |
| `form_annex` | **제출 서식·별첨 양식.** 식별 특징: 빈 칸과 서명·날인란 — 입찰참가신청서, 제안서 표지, 청렴계약이행서약서, 가격제안서 양식, 실적증명서(서식 제N호), 산출내역서, 인력투입계획표. 「서식 제N호」, 채워지지 않은 밑줄, 「(인)」. **경계:** 값을 뽑는 게 아니라 **「무엇을 몇 부 내야 하는가」의 목록**을 만드는 것이 목적이다. |
| `others` | 참고자료·현황자료·도면·기존 시스템 설명서·회의록·정정공고. **경계:** 「자동 분석 대상 아님 — 사람이 확인」으로 라우팅. 억지로 다른 클래스에 넣지 않는다. |

### 5-3. Extract 스키마 — 필드 작법은 Federal RFPs 규칙 그대로

정규화 강제(`"열거형 중 정확히 하나"`) · 날짜 `ISO YYYY-MM-DD` · 금액 `"콤마·원 표기 없이 정수 문자열"` · 폴백 사다리 · **`"없으면 빈칸 — 지어내지 않는다"`**

🔴 **Federal RFPs에 없고 우리에만 있는 필드** (= 한국 조달 고유 = 차별점)

| 필드 | 왜 |
|---|---|
| `참가자격[]` 각 항목의 **`자격인가_가점인가`** | 금융권 발주처 A 실물 사고를 잡는 한 칸 |
| `요구사항[]`의 **`단서_※[]`** | 151개 중 136개, 뜻 반전 24개 |
| `금지표현[]` | 「가능하다·고려할 수 있다」 → **평가에서 불가능으로 간주.** 미국 RFP에 이 개념이 없다 |
| `제출물[]` (이름·**부수**·분량상한·유효기간·별첨양식여부) | 43부 |
| `작성양식_지정` (지정/자유/불명) | 지정인데 못 받으면 43부 재출력 |
| `기술가격_비율` · `기술평가_하한` · `등급환산표` | 기술 90:가격 10 + 85% 컷오프 |
| `제출방법` (인편/전자/우편) · `제안발표`(발표자·분·인원) | 인편이면 이동 시간이 임계경로에 들어간다 |

### 5-4. Instruct 4단 체인 — p21 패턴 (`return this output verbatim`)

Federal RFPs가 2단 체인(`prep_kit → risk_triage`)을 쓴 것을 확인했으므로 **4단으로 간다.**

```
Instruct-1 자격판정   입력: Extract(공고문+제안요청서) + 회사 프로필(고정 파일)
  프롬프트 뼈대 ─ "당신은 제안 전략 컨설턴트가 아니라 대조기다. 판정 어휘는 셋뿐이다:
                 충족 / 미충족 / [확인필요]. 모든 판정에 근거 페이지를 붙인다.
                 회사 프로필에 없는 실적·자격을 만들지 않는다. 법령을 해석하지 않는다.
                 return this output verbatim with the bracketed sections filled in:
                 ## 판정: [Go / No-Go / 조건부]
                 | 요건 | 자격/가점 | 판정 | 근거(프로필 항목 · 공고 pN) |
                 ## 미충족 시 결론: [한 문장]"
Instruct-2 조견표     입력: Extract(요구사항) → 행 단위 조견표 + ※ 보존 + 행수 검산
Instruct-3 WBS       입력: Extract(과업내용서+요구사항) → 작업패키지·선후행·산출물·요구사항ID 역참조
Instruct-4 임계경로   입력: Instruct-3 + Extract(공고문 일정·제출물) → CP + 제출 체크리스트
```

| **Idea Creativity (25)** | **WBS·임계경로를 내는 서비스가 0곳** · 평범한 답 다섯과 사용자가 안 겹침 · Federal RFPs가 멈춘 세 자리 | 🔴 클라이원트가 「추천+분석+요구사항표」를 이미 판다 → **그 셋을 자랑하지 않는다** |
| **Product Planning (25)** | 당사자가 팀 안 · Won't 표 · 화면 3장 · 6절 「기능 하나로 잘랐다」 | 🔴 **외부 당사자 인터뷰 0건** |
